# PiCC report, 2026-09-18: two new tasks and a strict-typing contrast

For the project owner. Detail in `analysis/report.md` §16; numbers from
`analysis/v10_results.py`.

## What was built

Two new automatically verifiable greenfield tasks, alongside the untouched
chapters 1-10 task:

- **SQL engine (PiSQL).** An in-memory SQLite-compatible subset, scored on 30
  whole sqllogictest scripts pinned by git revision, against the pinned SQLite
  of the image. `studies/sql/README.md`.
- **Chapters 1-18 C compiler.** The core of *Writing a C Compiler* chapters
  1-18, 949 upstream tests, with library partner units, assembly helpers,
  headers, and `-lm` handled on the evaluator side. `studies/c18/README.md`.

Both reuse the existing runner, adapters, snapshots, logging, budgets, and
reporting. Test selections are committed and the fetch scripts refuse drift.
Both evaluators were verified before any model run, with reference-backed
candidates (GCC; Python's `sqlite3`) and deliberately wrong ones (reject-all,
constant-output).

## What was measured

Eighteen runs over 36 hours, three conditions per task (Rust, plain Python,
Python under `mypy --strict`), three replicates each.

| | SQL best | chapters 1-18 best | chapters 1-10 (v6-v9) |
|---|---:|---:|---:|
| Hidden score | 0.795 | 0.501 | 0.93-0.97 |

**The headline is task difficulty.** Chapters 1-10 has been saturated for four
batches, so it cannot show an improvement. Both new tasks sit well above their
floors and well below saturation, which is the lever the v8 report asked for.

**Strict typing looks costly on the harder tasks.** The planned in advance
criterion for an effect is met on SQL: typed minus plain Python is -0.754,
-0.659, -0.795. The mechanism is the gate, not the annotations: three of six
typed runs wrote substantial programs that `mypy --strict` rejected (13, 27
and 71 errors). In v7, on the easy task, the equivalent TypeScript gate was
cleared routinely and made no difference. Reading: a strict type gate is free
when the task is easy and binding when it is hard, at a fixed budget.

## Why this is a hypothesis, not a settled result

Ten of eighteen runs scored zero, mostly for reasons unrelated to their
condition. Four harness interactions did the damage, two recorded as
amendments during the batch:

1. A context-overflow recovery failure that leaves a run emitting truncated
   thinking blocks with no tool calls for the rest of its budget (5 runs).
2. The stall rule ending runs at 91 of 120 minutes while they were still
   working, including all three Rust compiler runs, each left with a complete
   module tree and no entry point.
3. A workspace-wide Python audit that zeroed two working runs for their own
   test drivers. Corrected and re-scored after the batch; this moved one run
   from 0.015 to 0.756.
4. Evaluation cost on the 668-test compiler partition, which excluded one run
   and is charged to the runs' wall budgets.

## Recommendation

Fix the four items, then replicate. The fixes are small and listed in
`analysis/report.md` §16.5; each needs a new manifest id and a fresh
experiment plan. The infrastructure itself is sound: the evaluators behaved
correctly on every reference and adversarial candidate, and the two defects
found were in scoping and pacing policy, not in the scoring.
