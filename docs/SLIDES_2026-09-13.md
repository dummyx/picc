# What changes the compiler a coding agent builds?

A controlled study of LLM coding agents, programming languages, and software-engineering practice

Draft, 2026-09-13. 20-minute talk.

---

## Why do this

Software engineering has asked for decades:

- Does a better specification improve the outcome?
- Do tests, and test feedback, produce better code?
- Do static types catch enough to matter?

With humans these are nearly impossible to test: people are expensive, vary a lot, and cannot be reset.

An LLM agent can be reset to the same state and run again. Same weights, same prompt, same empty repository. **The old questions become experiments.**

---

## Why not a benchmark, and why our group

Benchmarks rank models on fixed tasks: "which model is better?"

We hold the model fixed and vary the environment: **what changes the outcome?**

- **PL**: a way to measure whether types help, that we could never run on humans.
- **SE**: agents now follow, or ignore, our process advice. Which advice still applies?
- **Agents**: the harness is a research object. What the agent is given shapes what it does.
- **Method**: one GPU, one open model, open-source harness. A small lab can do this.

---

## What makes it hard

1. **Runs are expensive and few.** Two GPU hours and about 600k tokens per run. 71 runs took three weeks. Only large effects are detectable.
2. **The agent is not deterministic.** Two runs of the same condition can differ more than two conditions do.
3. **"Correct" is easy to game.** The agent sees tests, can overfit them, can call GCC, can embed answers.
4. **The apparatus has more parts than the experiment.** Agent framework, container, model server, evaluator, preprocessor. Any one can move a score more than the effect.
5. **Small n invites self-deception.** Eight runs will support any story you like.

---

## The one-line result

> Eight batches, 71 runs, one factor changed at a time.
> **No factor changed how correct the compiler was.**
> **Every factor changed how the agent worked.**
> One exception with a mechanism: an agent without tests may stop checking against the real machine.
> And the measuring apparatus was the hardest part.

---

## The task

- Start from an **empty repository**. Build a **C compiler** that emits x86-64 assembly.
- Chapters 1–10 of *Writing a C Compiler* (Nora Sandler): operators, variables, `if`, loops, functions, file-scope variables.
- Rust, standard library only. One batch used TypeScript vs JavaScript.
- Output must assemble with GCC and run.

Why a compiler: long-horizon, well-specified, mechanically checkable, hard to fake.

---

## The setup

| Piece | Choice |
|---|---|
| Agent | Pi coding agent, one persistent session, standard file and shell tools |
| Model | Qwen3.8-27B, 4-bit, local llama.cpp on one RTX 5090 |
| Budget | about 90 active minutes in two 45-minute rounds |
| Isolation | Docker image and model file pinned by hash |

The agent sees the spec, workflow instructions, 70% of the test suite, and a tool that runs those tests.

The agent never sees the hidden 30% or the fuzz oracle.

---

## Measuring correctness

**Corpus oracle**: 104 hidden tests. Valid programs must match GCC's output; invalid ones must be rejected. Averaged per stage, then across stages.

**Fuzz oracle**: 100 random C programs per stage, fixed seed, compared against GCC. Catches compilers that memorized test shapes.

**Guardrails**: a source audit for cheating (a hit scores 0), a repository snapshot after every round, and provenance hashes for image, model, evaluator, and test suite. Scoring runs outside the container after the run.

---

## Design and experiment plan

- One baseline; each treatment changes exactly one thing.
- **Paired replicates**, primary statistic = median of paired differences.
- Noise band fixed in advance: a difference under **0.13** is "no effect".

Before the first run of each batch: hypothesis, endpoints, analysis, and exclusion rules written down; manifest frozen and hashed; both committed.

During a batch: no edits, no peeking at hidden scores, every change logged as a dated amendment.

---

## The factors

| Batch | Factor | Variant vs baseline |
|---|---|---|
| v2 | prompt and specification | minimal prompt; brief spec; spec plus prescribed architecture; spec inline |
| v3, v5, v6 | test access | tests withheld entirely |
| v4, v7 | static typing | TypeScript strict vs plain JavaScript |
| v8 | test feedback | full test report pushed to the agent every 10 minutes |
| v9 | spec detail × tests | 143-word spec vs full spec, crossed with tests on / off |

v2–v5 ran on a harness later found to be noisy. v6–v9 ran clean.

---

## Result 1: nothing changed correctness

Paired median, treatment minus baseline:

| Batch | Factor | Corpus | Fuzz | Harness |
|---|---|---:|---:|---|
| v2 | prompt / spec strategies | within 1 sd | at ceiling | noisy |
| v3 | tests withheld | **−0.136** | −0.238 | noisy |
| v4 | TypeScript vs JavaScript | +0.026 | 0.000 | noisy |
| v5 | tests withheld | −0.022 | −0.044 | noisy |
| v6 | tests withheld | −0.017 | 0.000 | clean |
| v7 | TypeScript vs JavaScript | +0.004 | +0.001 | clean |
| v8 | pushed test reports | −0.025 | −0.002 | clean |
| v9 | minimal spec (with / without tests) | −0.070 / +0.046 | −0.020 / +0.200 | clean |
| v9 | tests withheld (full / minimal spec) | −0.104 / −0.067 | **−0.200** / +0.016 | clean |

The v3 effect did not replicate; its cause comes later. The v9 fuzz effect has a mechanism (next slides).

---

## Result 1, said plainly

On the clean harness the compilers are indistinguishable:

- corpus scores cluster between 0.88 and 0.97 for every compiler that was checked against the real assembler,
- fuzz scores at or near 1.0,
- the two arms of every contrast interleave.

The model **saturates** this task in 90 minutes, whatever it is told or given.

---

## Result 2: every factor changed the work

| Factor | Process effect |
|---|---|
| tests withheld | +100 turns, +500 lines of compiler, own test scripts instead of the tool |
| pushed test reports | on-demand test calls halved, self-written tests ×10, +10% turns |
| strict typing | +40% source, self-written tests ×10, 20+ type-checker runs, fewer turns |
| specification strategies | +50–90% output tokens for the same result |
| minimal prompt | matched the full workflow prompt in every replicate |

Time and correctness stayed flat. The agent changes its **method**, not its result.

---

## Result 2: a 143-word spec is enough

v9 replaced the 114-line specification with 143 words: the command line, what to output, ten one-line stage names. No precedence rules, no calling convention, no rejection rules, no mention of the book.

| Cell | Corpus | Fuzz vs GCC | Compiler size |
|---|---:|---:|---:|
| full spec, tests | 0.97 | 1.00 | 2159 lines |
| minimal spec, tests | 0.90 | 0.98 | 3529 lines |
| minimal spec, no tests | 0.88 | 0.996 | 3918 lines |

- Random-program agreement with GCC is unchanged. The model already knows C; the document adds nothing it needs.
- The corpus loss is invalid programs wrongly accepted: which malformed programs count as errors is a convention of the test suite, not of C.
- The compiler grows 60–80%: the agent builds pointers, shifts, and types nobody asked for.

---

## Result 2: the agent compensates

- With the test tool: calls it 11–24 times per run.
- Without any tests: every run writes its own tests, 50–170 C programs, or in two v9 runs a simulator of the machine.
- With reports pushed to it: writes tests to **reconstruct** the failing cases the report names but does not show.
- With strict types: an order of magnitude more self-tests, type checker after nearly every change.

Testing is where the agent puts its effort when the harness does not.

---

## Result 3: where tests do matter

v9, full spec, tests withheld, three runs:

| Run | Assembler calls | What it tested against | Fuzz vs GCC |
|---|---:|---|---:|
| 1 | 0 | its own x86-64 simulator crate | 0.80 |
| 2 | 54 | the real assembler and linker | 1.00 |
| 3 | 0 | its own 1500-line interpreter | 0.20 |

Run 3's compiler passes its own tests and emits assembly that GNU as rejects from stage 3 on: 800 of 1000 programs.

- The agent is a reliable oracle for C semantics, which it knows.
- It is not a reliable oracle for assembler syntax, which it must check empirically.
- Every minimal-spec agent went to the assembler. The detailed spec let the agent believe it knew the target.

Paired median −0.20, two of three replicates beyond the threshold: a candidate effect, with a mechanism, awaiting replication.

---

## Result 4: what correlates with correctness

Rank correlation with the fuzz score, 35 runs from the noisy batches:

| Dimension | all runs | runs that never hung |
|---|---:|---:|
| output tokens | 0.56 | 0.24 |
| active minutes | 0.54 | 0.15 |
| turns, tool calls | 0.55 | 0.05 |
| idle minutes | −0.58 | −0.16 |

Every "more work, better compiler" signal was really "the run did not stall". Among runs that never stalled, every fuzz score was at least 0.95.

Side note: 96–99.6% of generated characters were the model's thinking, not code.

## The harness was the experiment

Eight measurement defects, each large enough to fake a result:

| Defect | Effect |
|---|---|
| output-token cap | throttled long answers |
| workspace-wide cheat audit (Node, then Rust) | zeroed clean compilers for test code outside `src/` |
| terminal round timeout | ended rounds early |
| `#ifdef` preprocessing artifact | one lexer gap dominated the spread |
| **shell tool with no default timeout** | agent blocked up to 45 minutes |
| round cap mid-refactor | final snapshot did not build |
| advisory audit note treated as failure | buildable compiler scored 0 |
| manifest audit over the whole workspace | compiler zeroed for its own test tooling |

Eight defects. Each found by a planned in advance check, fixed for the next batch, never the running one.

---

## Case study: the hang lottery

- The agent tests its half-built compiler by running compiled programs.
- A miscompiled loop never terminates.
- Pi's shell tool has no default timeout; the maintainer declined to add one.
- The session blocks until the 45-minute round cap.

Over the 20 runs of v3–v5:

- 2670 completed shell commands, 99th percentile 5 seconds
- 18 that never returned, in 14 of 20 runs
- median loss 34 minutes each, **8.9 of 40 budget hours**

---

## The fix and its effect

A pinned community package gives the shell tool a 120-second default. An explicit timeout from the agent still wins.

| | v5 (before) | v6 (after) |
|---|---|---|
| runs idle ≥ 5 min | 5 of 8 | 0 of 8 |
| corpus score range | 0.476–0.974 | 0.897–0.975 |
| fuzz below 0.9 | 3 of 8 | 1 of 8 |

The v3 "tests hurt" effect was a lottery over which arm drew the hangs.

After the fix the agent recovers by itself: *"t8 hangs, infinite loop. Let me inspect the emitted assembly."*

---

## Case study: the round cap

- The repository is snapshotted at each 45-minute cap.
- A cap in the middle of a refactor leaves a snapshot that does not build: score 0.
- v7: 2 of 8 finals. v8: 1 of 8.

Fix, planned in advance for v8: score the **last buildable snapshot**.

- v8 pushed-feedback run 4: final 0 / 0, last buildable 0.894 / 0.932.
- Its own pushed report showed a 0.98 compiler two minutes before the cut.

The endpoint rule is part of the design, not a post-hoc patch.

---

## What experiment plan bought

Without it the project would have "found":

- that prescribing an architecture hurts (one v2 run, reversed by replication),
- that withholding tests hurts (v3, exactly at threshold, an artifact of hangs),
- that typing helps, or hurts (one v7 replicate crossed the threshold each way),
- that a minimal spec zeroes a compiler (v9, two scoring bugs, rules declared before the corrected numbers were known).

Every defect was found by a check written before the data existed. Every correction was declared before the corrected number was known.

---

## What it means for PL and SE

**PL**: static typing did not change correctness for this agent and task. It changed the process: more code, far more self-tests, constant type-checker use, fewer turns. The type checker acts as a fast free oracle the agent leans on.

**SE**: specification detail and workflow prompts moved cost, not outcome, down to a 143-word spec. Tests moved method, not outcome, except where the agent cannot be its own oracle: without tests it may stop checking against the real machine.

Both claims are about a capable model on a task it already knows. The next task must carry rules the model cannot recall.

---

## What it means for evaluating agents

- Measurement dominated. Harness variance (hangs, caps) exceeded every treatment effect.
- Long-horizon runs need: bounded tools, snapshots, hidden oracles, provenance pins, a planned in advance endpoint rule.
- Runs are expensive, so n is tiny. Pairing and a pre-declared noise band are the honest minimum.
- Process metrics (turns, tool calls, self-tests, tokens) are the interesting dependent variables when the score saturates.

---

## Limitations

- One model, one task family, one agent harness.
- 3–4 replicates per arm: resolves differences of about 0.13, not 0.03.
- Stages 1–10 saturate in 90 minutes; the ceiling hides differences.
- Round-end snapshots discard work after the last buildable commit.
- Fuzz programs come from a grammar and do not cover all of C.
- Process metrics were exploratory, not planned in advance.

---

## Next steps

The lever is the task, not the factor:

1. **A task the model cannot recall**: the same C compiler with altered language rules (precedence, evaluation order, indexing), translated back to C for scoring.
2. **Replicate the tests effect**: a no-tests batch with more runs and assembler use as a pre-declared mediator.
3. Fallback: stages 11–20, or a shorter budget.

---

## Takeaways

1. For this model and task, prompts, specs, feedback, and types did not change the compiler, and a 143-word spec was enough.
2. They changed how the agent worked: turns, tokens, code size, self-testing.
3. The agent compensates: no tests means it writes its own. That works for what it knows (C) and fails for what it must check (the assembler).
4. The apparatus was the hard part. Eight defects, all caught by planned in advance checks.
5. Small-n agent experiments are credible only with experiment plan, pairing, and hidden oracles.
