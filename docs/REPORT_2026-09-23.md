# PiCC report, 2026-09-23: the v17 batch in full

For the project owner. This covers all 15 runs of the v17 batch: the SQL
engine task, five languages, three runs each. Every number here was measured
directly from the runs' own records:

- the agent's saved conversation (every reply, with the time it started and the
  time it was saved, and every command with its result);
- the live log of each reply as it was written (this keeps the model's
  reasoning text, which is how reasoning is counted);
- the harness's logs of rounds, snapshots, scores and blocked commands;
- the scorer's record for every test script;
- the files each agent left behind.

The measuring script is `analysis/v17_internals.py`; its output is
`analysis/v17-internals.json`. Scores come from `analysis/v17_results.py`.
Where this report differs from something said earlier, section 12 lists the
correction.

A **token** is the unit the model reads and writes: a short piece of a word,
roughly three to four characters of code.

## 1. Summary

- **15 runs, 2 hours of agent time each**, 30 hours in all, from
  2026-09-21 14:29 to 2026-09-22 22:09 UTC. Every run used its full two
  hours. Nothing broke: 5,762 replies, none lost to a server error, and all 259
  conversation summaries succeeded.
- **Scores** (0 to 1, on 8 test scripts the agent never saw): best 0.851
  (python-r2). Three runs scored at or near zero: python-r3 0.000,
  typescript-r1 0.000, typescript-r3 0.085. Middle run per language:
  JavaScript 0.793, Python 0.755, Python with strict type checks 0.527,
  Rust 0.445, TypeScript 0.085.
- **The spread inside each language is bigger than the differences between
  languages.** Whether type checking helps or hurts is still unanswered.
- **Low scores come from single all-or-nothing mistakes, not from generally
  weak engines.** python-r3 never read the file it was given. typescript-r1
  checked its code with a shortened command, changed its code to suit that
  wrong check, and so never passed the real one. typescript-r3 prints nothing
  for `CREATE TABLE` and `INSERT`, so every later answer is lined up against
  the wrong question. python-typed-r1 crashes on `NULL * number`, and because it
  prints nothing until the very end, one crash wipes out every answer in that
  script. rust-r3 crashes on `TRUE AND NULL` the same way.
- **One test script beat every engine.** It joins 4 to 64 tables at once, and
  no engine combines tables efficiently: they ran out of time or memory. So
  the highest score any of these engines could reach was 0.875; the best run
  got 0.851.
- **Where the time went: 85% was the model writing replies**, 13% was
  summarizing the conversation when it grew too long, and only about 1% was
  the agent's commands actually running. The agent almost never waits for its
  tools; it waits for the model. The model writes about 62 tokens a second, so
  two hours buys 340,000 to 410,000 tokens per run.
- **About 60% of everything the model wrote was reasoning** (thinking before
  acting). A typical reply reasoned for about 180 tokens and took about 7
  seconds. 96 replies reasoned up to the 8,192-token limit.
- **Every reply re-reads the whole conversation**, typically 78,000 tokens.
  Over a run that adds up to 15 to 36 million tokens read, 92–97% of it reused
  from the previous reply instead of recomputed.
- **The agent works in small steps**: 195 to 478 replies per run, almost every
  one ending in exactly one command. About half of its shell commands only look
  at its own code (`sed`, `grep`, `cat`).
- **Wasted work**: 6 replies of about 8 minutes each were thrown away because
  the model tried to rewrite its whole program in one reply and ran out of
  room. rust-r1 sent 4 file writes without a file name.
- **The agents tried to use the real SQLite in 14 of 15 runs** to check their
  guesses (blocked every time). One tried a web search tool that does not
  exist.
- **The rule checker wrongly blocked 4 legitimate commands in 3 runs**,
  because words inside code looked like forbidden commands. This is a defect in
  the setup (section 11).
- **Three agents declared themselves finished while far from done**, for
  example "complete and fully verified" at a score of 0.60. rust-r2 did so four
  times.

## 2. What was run

### The task

Each run starts from an empty folder. The instruction (identical for all runs
except the first three lines) asks for **PiSQL**: an in-memory SQL engine that
reads a file of SQL statements and must behave like SQLite on a stated subset:

> print, for each statement, one block on standard output: `ok N` followed by
> the N result rows (one row per line, column values separated by one tab), or
> `error MESSAGE` on one line when the statement is rejected.

The subset covers `CREATE TABLE` (with types such as `INTEGER`, `REAL`,
`TEXT`/`VARCHAR(n)`), `CREATE INDEX`, `INSERT`, and `SELECT` with joins,
`WHERE`, `GROUP BY`/`HAVING`, aggregates, subqueries, `ORDER BY`, and
`UNION`/`INTERSECT`/`EXCEPT`, all with SQLite's rules for NULL, number and text
handling. Using an existing database engine, subprocesses, or hard-coded
answers is forbidden.

### The five conditions

| condition | language | the build step the scorer runs | how the engine is started |
|---|---|---|---|
| python | Python | `python3 -m py_compile pisql.py` (syntax check only) | `python3 pisql.py INPUT.sql` |
| python-typed | Python with type annotations | `mypy --strict ... pisql.py` (strict type checker) | same |
| javascript | JavaScript | `node --check src/pisql.js` (syntax check only) | `node src/pisql.js INPUT.sql` |
| typescript | TypeScript | `tsc --strict --noEmitOnError --target es2022 --lib es2022 ... --types node --typeRoots ... src/pisql.ts` | `node dist/pisql.js INPUT.sql` |
| rust | Rust | `cargo build --release --offline` | `target/release/pisql INPUT.sql` |

If the build step fails, the engine is never run and the score is 0.
JavaScript and TypeScript were added to the batch part-way through (amendment
`9ff035f`), so their six runs ran last. The order was: python-r1,
python-typed-r1, rust-r1, rust-r2, python-r2, python-typed-r2,
python-typed-r3, rust-r3, python-r3, typescript-r1, javascript-r1,
javascript-r2, typescript-r2, typescript-r3, javascript-r3.

### What the agent had, and did not have

- Tools: read a file, run a shell command, edit a file, write a file, `grep`,
  `find`, `ls`. A shell command is stopped after 120 seconds.
- **No tests, no scores, no real SQLite, no internet.** The agent never saw a
  single test script or any score during the run. Everything it knew about
  SQLite's behaviour came from the model's memory.
- `AGENTS.md` and `TASK.md` in the folder were empty.
- After the first round, each new round began with one word: "Continue." The
  agent was never told how much time was left.

### Budget and rounds

Two hours of agent time per run. A round is stopped after 45 minutes, so a
normal run has rounds of 45, 45 and 30 minutes. A round also ends early if the
agent stops on its own (it declares it is done) or if a reply ends without a
command. After each round the harness saves a snapshot of the folder and
scores it.

### Model and server

- Model: Qwen3.8-27B, 4-bit NVFP4 checkpoint `RadixArk/Qwen3.8-27B-NVFP4`,
  revision `319f741c`.
- Served on this machine by SGLang 0.5.20 on one RTX 5090, configuration #4 in
  `docs/INFERENCE_SGLANG.md`.
- Conversation limit 131,072 tokens. One reply may be at most 32,768 tokens,
  of which at most 8,192 may be reasoning. Randomness setting (temperature)
  1.0, so two runs of the same condition differ by chance.
- When the conversation passes about 90,000 tokens it is summarized: the
  latest ~49,000 tokens are kept word for word and everything older is replaced
  by a written summary.
- Agent program Pi 0.85.1; harness image `picc-experiment:0.5`; study manifest
  `picc-sql-minimal-v7`; harness commit `238dab0`.

### Scoring

- **8 held-out test scripts** from SQLite's own test collection
  (sqllogictest). Each script creates tables, fills them, and asks queries; the
  scorer checks every answer against the answer recorded in the script, after
  first re-running the script in SQLite 3.40.1 and dropping any recorded
  answer SQLite does not reproduce. 51,939 checks in total.
- A script's score is the share of its checks answered correctly. **The run's
  score is the plain average of the 8 script scores**, so a script with 187
  checks counts as much as one with 10,000.
- 22 further scripts (187,239 checks) are scored after every round to follow
  progress. The agent never sees these either.
- "Working engine" below means a score above 0.0503, which is what an engine
  gets by printing the same fixed reply for every statement.

## 4. Why the low scores are low

Each of these was checked in the records, and where the stored error message
was cut short, by running the saved engine again on the same input.

### python-r3: 0.000. It never read its input.

The task says the engine is started as `python3 pisql.py INPUT.sql`, with the
file name after the program name. python-r3's engine never looks at that name.
Its `main()` reads:

```python
path = os.environ.get("PISQL_INPUT", "INPUT.sql")
```

so it always opens a file literally called `INPUT.sql` in the current folder.
The agent had created such a file itself: a 6-statement sample
(`CREATE TABLE t ...; INSERT INTO t VALUES (1,'one',1.5),(2,'two',2.5); ...`).
The scorer runs each engine from its own folder, so for every one of the 8
scripts the engine answered the agent's sample instead of the test. The scorer's
first complaint is identical on all 8 scripts, a row from that sample:
`line 5: malformed block header "2 'two' 2.5"`.

Two more mistakes would have cost it anyway: columns separated by a space
instead of a tab, and text printed in quotes (`'two'`) instead of as is.

Why the agent never noticed: it ran its engine in 100 commands. In 98 it chose
the input by setting `PISQL_INPUT=...` in front of the command, in 2 it fed a
file on standard input. **Not once did it start the engine the way the task
says**, with the file name after it. Its engine may well be a reasonable
engine; it was never measured.

### typescript-r1: 0.000. It checked against the wrong settings and never built.

The task gives the full build command, including `--target es2022 --lib es2022
--types node --typeRoots /usr/local/lib/node_modules/@types`. typescript-r1
ran the TypeScript checker 23 times, always as the short form
`tsc --strict --rootDir src --outDir dist src/pisql.ts`. Without those
options the checker assumes the old 2009 version of JavaScript and knows
nothing about Node.js. Its first check reported `Cannot find module 'fs'`,
`BigInt literals are not available when targeting lower than ES2020`, and
`Cannot find name 'Buffer'`.

The agent took this at face value. 19 of its replies reason about staying
within the old version ("ES5 syntax: no `for...of` over strings/typed arrays,
no spread (argument spread is OK), no `.includes()`, use a dictionary instead
of Map/Set"), and it declared Node's built-in names by hand at the top of its
file:

```ts
declare function require(name: string): any;
declare const process: { ... };
declare const BigInt: any;
```

Under the real build command, Node's own definitions are loaded, and these
three lines clash with them. The scorer's build ended with exactly three
errors, all from those lines:

```
src/pisql.ts(4,18): error TS2300: Duplicate identifier 'require'.
src/pisql.ts(6,15): error TS2451: Cannot redeclare block-scoped variable 'process'.
src/pisql.ts(14,15): error TS2451: Cannot redeclare block-scoped variable 'BigInt'.
```

It had 21 errors after round 0 and 3 after rounds 1 and 2. Its 4,335-line
engine was never run, so its quality is unknown. It also lost two replies
(16.6 minutes) to whole-file rewrites that were cut off (section 6).

The other two TypeScript runs avoided this by writing a TypeScript settings
file (`tsconfig.json`) that includes Node's definitions, and checking with that
(typescript-r2: 59 of 65 checks; typescript-r3: 47 of 48).

### typescript-r3: 0.085. A stray brace at the stop, then no replies to CREATE and INSERT.

Round 0 failed to build with 72 errors. The cause was one extra `}`. The
agent's last edit of the round, saved about one second before the 45-minute
stop, added a new case after the `isnull` case but left that case's old closing
brace in place. Removing that one brace from a copy of the snapshot and
checking it again in the pinned image gives zero errors: all 72 came from it.
The agent had no chance to check the edit.

It built from round 1 onward, but the engine prints nothing at all for
`CREATE TABLE`, `INSERT` and `CREATE INDEX`. The task says every statement gets
one block, and a statement that returns no rows prints `ok 0`. Its main loop
prints only for queries and errors:

```ts
case "createTable":
  execCreateTable(db, st);
  break;
case "insert":
  execInsert(db, st);
  break;
case "query": {
  const res = execQuery(st.q, db, null);
  out(`ok ${res.rows.length}`);
```

Rebuilt in the pinned image and run on the scorer's own input, it printed
10,021 blocks for the 10,051 statements of the orderby script and 10,000 for
the 10,012 of the expr script. From the first `CREATE TABLE` on, every answer
is compared with the wrong statement, so almost everything counts as wrong. The
error messages the scorer lists for this run ("no such column: all",
"expected )") therefore belong to other statements than the ones they appear
against. A six-statement test (`CREATE TABLE`, `INSERT`, `CREATE INDEX`,
`SELECT`, `DROP TABLE`, `SELECT`) gives three blocks.

It also cannot read `VARCHAR(40)`: every `CREATE TABLE` in select5 fails with
"expected identifier". Earlier, its first whole-file write had been cut off
(section 6); it then wrote the engine as four part files and joined them, and
the four parts are still in `src_parts/`.

### python-typed-r1: 0.134. One missing NULL check, and a checker told not to look.

Its final engine stops with an error on 5 of 8 scripts. Running it again gives:

```
TypeError: unsupported operand type(s) for *: 'NoneType' and 'int'
```

In its arithmetic code, the NULL check happens only when one side is text.
`NULL * 5` skips it and reaches `asfloat(na) * asfloat(nb)`, where

```python
def asfloat(v: object) -> float:
    return cast(float, v)
```

`cast` tells the type checker "treat this as a number" without checking
anything. So the strict type checker, which is the build step for this
condition, passed code with exactly the kind of mistake it exists to catch.
This engine uses `Any` (the type that switches checking off) 195 times and
`cast` 8 times; the other two typed-Python engines use `Any` 8 and 0 times and
`cast` never.

The damage is total per script because of how the engine prints: it collects
all its output and prints it once at the end, and it only catches its own error
type. One unexpected error on one statement means nothing at all is printed
for that script. Its held-out score was 0.295 after round 0, when three scripts
already crashed this way, and 0.134 after rounds 1 and 2, when five did.

It also cannot read `VARCHAR(40)`, and it prints one extra blank line at the
end, which the scorer marks as a format error (the answers before it still
count).

### rust-r3: 0.341. A case the author thought impossible.

Three scripts end with:

```
thread 'main' panicked at src/engine.rs:1135:14:
internal error: entered unreachable code
```

That line is in its three-valued `AND`:

```rust
match (truth(a), truth(b)) {
    (Some(false), _) => Val::Int(0),
    (Some(true), Some(false)) => Val::Int(0),
    (Some(true), Some(true)) => Val::Int(1),
    (None, Some(false)) => Val::Int(0),
    (None, Some(true)) => Val::Int(1),
    (None, None) => Val::Null,
    _ => unreachable!(),
}
```

`TRUE AND NULL` is missing, so it falls into `unreachable!()`, which stops the
program. (The line for `NULL AND TRUE` is also wrong: it should give NULL, not
1.) Like the Python engines, it prints everything at the end, so each crash
erases the whole script.

### python-r2 after round 1: a snapshot taken in the middle of a change

python-r2 scored 0.83, then 0.12, then 0.82. Running its round-1 engine again
gives `ValueError: not enough values to unpack (expected 5, got 4)`: at the
45-minute stop it had changed an internal record from four fields to five in
one place but not yet in the other. Its engine crashed on every progress
script. It finished the change in the next round. Had the final stop landed at
such a moment, this run, the best of the batch, would have scored 0.231 (its
held-out score at that snapshot) instead of 0.851.

### The pattern

| what sank the score | runs |
|---|---|
| never read the input it was given | python-r3 |
| no reply to `CREATE TABLE` and `INSERT`, so answers line up with the wrong questions | typescript-r3 |
| checked with a shortened command, adapted to the wrong settings, never built | typescript-r1 |
| snapshot taken mid-edit | typescript-r3 (round 0), python-r2 (round 1 only) |
| one unexpected error erases a whole script's output | python-typed-r1, rust-r3, python-typed-r3 (one script, `IndexError`) |
| cannot read `VARCHAR(40)` | python-typed-r1, python-typed-r3, typescript-r3 |
| no efficient way to join many tables | all 15 (select5) |

Two of these (python-r3, typescript-r3) are failures to follow the output and
input rules stated in the first paragraph of the task, not failures of SQL.

written tokens, of which about 60% is reasoning. Faster commands would change
almost nothing. Fewer or shorter summaries, or a faster server, would.

## 9. How the agents behaved

### They tried to use the real SQLite

14 of 15 runs tried to reach SQLite to check what it really does, 18 attempts
in all, mostly `which sqlite3` or `python3 -c "import sqlite3"`. All were
blocked. Some were specific experiments: javascript-r2 wanted to check what
SQLite returns for `3.0` and `1e20`; python-r2 wanted to see what happens when
the number 5 goes into a `TEXT` column. The run without an attempt, rust-r3, instead
called a web search tool that does not exist, with the query
`SQLite "SELECT '1' + '1'" result typeof real or integer text operand
arithmetic`, and got "Tool web_search not found".

This is the clearest sign of what the agents lacked: they knew their guesses
about SQLite's behaviour were uncertain and looked for a way to check them.

### Other blocked commands

| what was blocked | count | runs |
|---|---:|---|
| using SQLite | 18 | 14 runs (all but rust-r3) |
| writing outside the work folder (`/tmp`) | 4 | rust-r1 (3), typescript-r2 (1) |
| looking at environment variables (`env \| grep ...`) | 1 | python-r3 |
| looking at the harness's own folder (`/run-artifacts`) | 1 | python-r3 |
| looking for the test folder (`ls /visible-tests`) | 1 | javascript-r2 |
| **wrong blocks (legitimate commands)** | **4** | python-typed-r1 (2), rust-r2, typescript-r1 |

python-r3 (24 minutes in) and javascript-r2 (37 minutes in) each looked once
for tests or harness files; neither found anything and neither tried again.

### The four wrong blocks

The rule checker searches the whole text of a shell command, including code
the agent is pasting into a file:

| run | blocked as | what actually triggered it |
|---|---|---|
| python-typed-r1 (twice) | "environment inspection" | a Python pattern `(list\|dict\|set\|tuple)` in a fix-up script: `\|set` looked like the shell command `set` |
| rust-r2 | "running an existing database engine" | a code comment `// %.15g leaves no decimal point; SQLite adds ".0"`: `; SQLite` looked like running `sqlite` |
| typescript-r1 | "use of a C compiler" | TypeScript code `cc >= 0xd800 && cc <= 0xdbff` inside a 32,088-character append: `& cc` looked like the C compiler `cc` |

Each agent noticed ("Weird — the experiment guard rejected this ... this is a
false positive") and got around it within one or two commands, by writing the
script to a file or using the edit tool instead. The cost in this batch was
small, but the checker can block any command that happens to contain such
text.

### They declared themselves finished too early

Six times an agent stopped on its own with a summary of its work:

- rust-r2, four times in a row, each after a new round began with "Continue":
  "The implementation is complete and fully verified", "All green", "All
  green", "Session complete". Its score was 0.60 throughout.
- python-typed-r2: "All green. The implementation is complete and verified"
  (score then 0.71).
- typescript-r2: "PiSQL is complete and fully verified" (score 0.76).

"All green" means the agent's own checks passed. With no access to real tests,
its checks cover only what it thought of, so it has no way to see what it is
missing. Each time, the harness started a new round and the agent went back to
work, so no time was lost beyond the short summary reply.

### How they tested without tests

Every agent wrote its own SQL inputs and checked the engine's output against
what it believed SQLite would print. Test files left behind range from 0
(typescript-r1, rust-r3) to 72 (typescript-r3). Agents ran their engine 24 to
132 times per run. Several wrote small runner scripts; none had anything to
compare against except its own expectations. The two output-rule failures show
the limit of this: python-r3 ran its engine 100 times without once starting it
the way the task says, and typescript-r3 ran its engine 101 times without
noticing that `CREATE TABLE` and `INSERT` printed nothing.

### How often they ran the build check

Commands including the type-check or build: typed Python 34–41 per run,
TypeScript 27–64, Rust 30–60, untyped Python 13–40, JavaScript 26–40. The typed
conditions did not check dramatically more often than the untyped ones.

## 11. Problems in the experiment setup

These are problems with the harness, not with the agents. None invalidates a
run in this batch; the first two should be fixed before the next one.

1. **The rule checker blocks legitimate commands** (4 blocks, 3 runs,
   section 9). It matches forbidden words anywhere in the command text,
   including code and comments being written to a file. It should look only at
   the commands themselves, not at quoted or pasted file contents.
2. **Crash messages are stored cut short.** The scorer keeps only the first
   part of an engine's error output, so the actual error line (for example
   python-typed-r1's `TypeError`) is lost and had to be recovered by running
   the engine again. It should keep the end of the output, where the error is.
3. **The score is taken wherever the stop lands.** A snapshot taken during a
   half-finished change can score far lower than the engine a minute earlier or
   later (python-r2 round 1: 0.231 held-out between 0.830 and 0.851;
   typescript-r3 round 0: no build at all). All
   15 final snapshots happened to be taken at clean moments, but nothing
   guarantees it, and the "last snapshot that builds" backup rule does not help
   when the code builds but crashes. This is a design question, not a bug.
4. **The scorer's label "wrong format" hid python-r3's real problem** (it never
   read its input). A check for "the same output for every script" would have
   named it directly.
5. Reasoning tokens are still recorded as 0 in every run (known; counted with
   the tokenizer here).
6. **Summaries come every 5 to 9 minutes and take 13% of the time.** This is
   a setting, not a bug: about 49,000 tokens are kept word for word and the
   summary point is about 90,000, which leaves only about 21,000 tokens of room
   between summaries. Keeping less, or allowing a longer conversation, would
   mean fewer summaries; whether the agent then works better is untested.

## 13. What this batch does and does not show

**It does show:**

1. **The harness now holds up.** 30 hours, 5,762 replies, no server errors,
   no failed summaries, 6 replies cut off (0.1%). The batch before this one
   (v15) could not be analysed; this one can.
2. **Scores here are decided by a few all-or-nothing mistakes**: reading the
   wrong input, skipping the reply to `CREATE TABLE`, checking with the wrong
   settings, one missing case that crashes the program, a snapshot taken
   mid-edit. Each can turn a mostly working engine into a zero or near-zero.
   Most are not about SQL at all; the two crashes are small SQL mistakes whose
   damage is multiplied by the engine printing nothing until the end.
3. **The agents cannot see these mistakes**, because they have no tests and no
   SQLite. Their own checks pass; they report "complete and fully verified" at
   0.60. python-r3 ran its engine 100 times without once starting it the way
   the task says, and typescript-r3 ran its engine 101 times without noticing
   it printed nothing for `CREATE TABLE`.
4. **Time is bound by how fast the model writes.** 85% of the budget is spent
   writing replies and 13% summarizing. Commands take 1%.
5. **`mypy --strict` and `tsc --strict` are not the same kind of gate.** The
   Python checker never failed a snapshot (0 of 10) and let a crash through
   because the code told it not to look (`cast`). The TypeScript checker failed
   4 of 9 snapshots: typescript-r1's three, caused by the agent checking against
   different settings than the real build, and typescript-r3's first, caused by
   the stray brace at the stop.

**It does not show:**

- **Whether type checking helps or hurts.** Both comparisons cross the line set
  in advance ("typing hurts", −0.33 and −0.38), but each rests on two pairs
  that disagree (−0.62 against −0.03; −0.71 against −0.05), the spread inside
  one language (0.17 to 0.85) is larger than the claimed effect, and the
  collapses traced in section 4 have specific causes: a missing NULL check
  hidden by `cast` (python-typed-r1), and an engine that prints nothing for
  `CREATE TABLE` and `INSERT` (typescript-r3). The second has nothing to do
  with types. Three runs per condition cannot separate a real effect from this
  kind of luck.
- **Which language is best.** JavaScript has the best middle score (0.793) and
  no zero, but the same caution applies.

**If the question is to be answered**, it needs many more runs per condition,
the setup fixes in section 11, and scores reported in two parts: whether the
engine passed its build and ran on its input at all, and how good it is when it
did. Mixing the two is what makes the current numbers so noisy.

## 14. How each number was measured

- **Time split** (section 5): each saved item in the conversation file closes
  a time slice that began when the previous item was saved. A reply's slice
  starts at its own start time; a command result's slice is the command running;
  a summary's slice is summarizing. Whatever remains between the last saved item
  and the round's end is the reply killed at the stop. Every run adds up to its
  120 minutes.
- **Tokens written and read**: from the usage figures the server returned for
  each reply, as saved in the live logs. "Read" is the full conversation sent
  with each reply; "reused" is the part the server did not have to recompute.
- **Reasoning tokens**: the reasoning text of each reply, re-assembled from the
  live logs and counted with the model's own tokenizer
  (`~/models/Qwen3.8-27B-NVFP4/tokenizer.json`).
- **Summary costs**: the server's usage for each summary request, kept in the
  conversation file; the time as above.
- **Tool calls and failures**: every command in the conversation file with its
  result and error flag. Shell purposes are assigned by the patterns in
  `bash_labels()` in `analysis/v17_internals.py`.
- **Scores**: the scorer's per-script records under
  `runs/<run>/artifacts/evaluations/`.
- **Engine measures**: the files in each final workspace. The engine is
  `pisql.py` for Python and the run's own-language files under `src/` for the
  other languages. Function counts for JavaScript and TypeScript are
  approximate (pattern-based).
- **Causes in section 4**: read from the saved engine code, and where the
  stored error was cut short, by running a copy of the engine from the relevant
  snapshot outside the run folder, on exactly the input the scorer gives it
  (built with the scorer's own `statements_of` and `script_input` functions).
  typescript-r3 was rebuilt with the real build command inside the pinned image
  and run there with no network.

To regenerate the numbers: `.venv-sglang/bin/python analysis/v17_internals.py`
(about 10 seconds; the tokenizer package lives in the SGLang environment).
